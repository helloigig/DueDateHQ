## A · Overrides to the base handoff

Apply these in place of the noted sections.

### A1 · Heatmap — reframe as micro-calendar (overrides §5.1 D7)

**Before:** hide until ≥ 30 upcoming.
**Now:** keep visible at the current threshold, but **change its job.** Clicking a dense cell opens a **day-detail popover** listing the deadlines for that day. Extend backward one row (last week) so completion pace is visible.

**Acceptance:**
- Clicking any non-empty cell opens a popover pinned to the cell with a list of deadlines (client · form · status · quick-complete button)
- Popover closes on Esc, outside-click, or the cell being clicked again
- Rendering order: last-week row → today row → 7 forward weeks

### A2 · Bell = unified notification center (overrides §5.3 T3)

**Before:** bell linked to alerts list only.
**Now:** the bell dropdown is a **unified notification center**. Filter chips inside. Each item routes to its relevant detail screen.

Contents:

- Extension-filing confirmations (Q29)
- Reminder-sent digests

The `/announcements` page remains the **historical archive** of state announcements only. The bell is real-time-across-types.

### A13 · "In progress" visual — half-filled dot (new)

The data model already tracks `in_progress` status. UI currently treats it identically to `not_started`.

**Fix:** in `DeadlineRow.tsx`, change the urgency dot to a half-filled variant (`◐` shape, but rendered as SVG per base handoff §5.10 reference) when `deadline.status === 'in_progress'`.

- Empty circle (`○`) → not started
- Half-filled (`◐`) → in progress
- Filled (`●`) → due today / overdue

Use the urgency tone color for the fill; the SHAPE communicates status, the color communicates urgency. Two independent axes, no conflict.

## B · New patterns not in the base handoff

These fill actual gaps, not overrides.

### B1 · Alert escalation ladder

When a state announcement is published and the CPA hasn't acted:

| Time since detection | Treatment |
|---|---|
| 0h | Email + in-app banner |
| 24h unactioned | Reminder email; banner stays |
| 48h unactioned | Banner darkens (use `bg-danger-bg` + `border-danger-border`); announcement also appears in the Priority Card as a high-score item |
| 72h unactioned | **Blocking dialog** on next dashboard open: *"6 clients still need review — Acknowledge or Snooze"* |

**Rules:**
- Never auto-apply changes on the user's behalf. Silence must be active, not passive.
- "Snooze" asks for a reason (text field) + default 24h snooze; logged per-firm for internal data quality
- Acknowledge = viewed the announcement detail, not applied action — so user can still dismiss if not applicable
- Blocking dialog respects `prefers-reduced-motion` (no dramatic animations)

**Implementation hook:** pipeline runs client-side on dashboard mount. State lives on the announcement record (`acknowledgedAt`, `snoozedUntil`).

### B2 · Confirm modal taxonomy (authoritative list)

**Confirm modal REQUIRED on:**
1. Batch-adjust deadlines from announcement (currently a bug — applies without confirm)
2. Archive client — show active-deadline count; warn if > 0
3. CSV import commit (final step of wizard)
4. Remove team member — show how many client assignments revert to Owner
5. Dismiss announcement — *not reversible gracefully*, explicit opt-in text: "I've reviewed this and none of my clients are affected"
6. Remove filing bundle from client — lists pending deadlines that will be deleted
7. Send batch notification email — preview recipient list + editable body before send
8. Undo import (within 7-day window) — shows N clients / M deadlines that will be wiped

**NO confirm modal on** (reversible + activity-logged):
- Mark complete · Mark in progress · Defer · File extension
- Add note · Edit note · Pin/unpin note
- Toggle filters · Toggle view modes

**Modal spec:** use the shell from base handoff §6.1 *Modal shell*. Destructive confirms use `bg-danger-solid`. Non-destructive use `bg-accent`.

### B3 · Same-client-same-day row grouping (confirms current code — don't refactor)

For same-client, same-day deadlines: **one row per deadline** (per-form status must stay independent), but suppress the client name on rows 2+, show a left-indent connector.

**Do NOT merge into one row.** That hides per-form status which is the thing the CPA acts on.

The existing code in `Dashboard.tsx:306-334` already implements this. Leave it. Apply the same treatment in `ClientDetail.tsx` upcoming/this-year lists when same-day deadlines exist.

### B4 · "+ New" dropdown scope (final)

Two items only:
- **New client** → AddClientModal
- **Import CSV** → navigates to `/import`

**Drop "New deadline"** from the global menu. It never makes sense without client context, so it belongs exclusively on the client detail page as a `+ Deadline` button.

### B5 · Add-deadline entry points

One path, two entries:
- **`+ Deadline` button on client detail page** (primary — you're already holding that client in your head)
- **Activity-log deep link** (secondary — e.g., clicking "Add deadline from this extension" in the Announcement Detail affected-client list, which pre-fills state/form)

**Never from Dashboard.** Dashboard is triage, not data entry.

### B6 · Client bundle/state/entity change — migration preview (new)

When a user changes a client's filing bundle, primary state, or entity type:

1. Show a **migration preview modal** before commit:
   ```
   Changing entity from LLC → S-Corp
   
   – Removes  3 pending deadlines (LLC-specific forms)
   + Adds     5 new deadlines (S-Corp forms)
   ✓ Keeps    2 overlapping deadlines (federal)
   
   [Cancel]  [Apply changes]
   ```
2. Never silently remove deadlines
3. Never silently duplicate
4. Activity log: single entry summarizing all three counts

### B7 · Notification preference (settings stub)

Per-user settings: email delivery mode for announcements.

- **8am digest** (default) — one email per morning with all state announcements from the last 24h
- **Per-alert** — email fires immediately when an announcement is detected

In-app banner fires regardless. SMS is **deferred to Phase 2** and NOT half-built in MVP.

### B8 · Export modal — what × format × recipient (new, addresses Q31)

Export buttons are currently decorative. Build a modal with three axes (PRD §3.4):

**Axis 1 · What**
- Current filtered view
- All active deadlines
- Specific date range (date picker)
- Specific client (when launched from client detail)

**Axis 2 · Format**
- PDF — client-facing deadline report with firm branding
- CSV — raw data, portability guarantee
- iCal (.ics) — subscription URL for calendar apps

**Axis 3 · Recipient**
- Download (default)
- Email to self
- Email to teammate (Team tier)

**Modal spec:** uses the shell pattern from base handoff §6.1. Radio groups for each axis. No multi-select within an axis — one choice per axis.

**Trigger locations:** Dashboard (This-Week section "Export" button — currently present but dead), Client Detail header `⋯` menu, Announcement Detail (export affected-client list).

### B9 · Extension state machine (extends PRD §3.7)

`filed_extension` status has two sub-states:

| Sub-state | Meaning | Visibility |
|---|---|---|
| `submitted` | CPA filed Form 4868/7004 to IRS or state | Client detail Activity tab entry |
| `approved` | IRS/state has acknowledged (manual toggle in R1; automated via IRS API in Phase 2) | Activity entry + badge on original deadline row |

Post-approval, the **extended-date deadline** already exists as a separate deadline object. Linking it to the original is via `extendedFrom: <originalDeadlineId>` on the new deadline record.

## E · What the parallel session got right (preserved for future-you)

Stylistic choices and decision principles worth baking in:

1. **Cite the doc.** Every decision in the parallel session referenced PRD §X or dashboard spec §Y. That's the mark of design grounded in product truth, not taste.
2. **Kill additive scope on sight.** Focus mode, Gmail, SMS, client portal, entity type on rows — all rejected with specific reasoning, not gut feel.
3. **Triage ≠ summary** (Q15). The dashboard's job is "what do I owe which client this week?" Any decision that drifts toward practice-health reporting breaks positioning.
4. **Confirm only when damage is hard to reverse.** Activity-logged reversible actions don't need modals. Destructive/propagating actions do.
5. **Silence must be active, not passive.** Apply to announcement handling (B1), to client changes (B6), to archival warnings.
6. **User-language in UI** (Filing bundle, Alerts) + product-truth in code/PRD (ServicePackage, state-deadline intelligence).
